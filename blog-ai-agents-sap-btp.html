Blog · SAP BTP & AI

From static reports to conversational insight

Using AI agents on SAP BTP to bridge SAP ECC data with the business user.

Aricord Consulting · 12 August 2026 · 6 min read

Key takeaways

  • The gap in most SAP ECC / BW estates isn't data — it's fast access to insight.
  • Plan-vs-actual variance analysis is one of the best first use cases for AI agents in SAP.
  • Data stays in ECC and BW; the agent queries it live — no shadow data model.
  • The agent reuses existing SAP role-based authorizations — no weaker "AI" permission layer.
  • Every question, query and result is logged to SAP HANA for audit and model governance.

The problem we keep seeing

Most organisations running SAP ECC — or SAP BW alongside it — have no shortage of data. Project revenue, cost, and margin figures are all sitting in the system, refreshed on schedule, ready for reporting. What's missing isn't data. It's access to insight.

A business user who wants to know why a project's margin slipped this quarter still has to raise a request to a BW/reporting analyst, wait for a query to be run or a report to be built, and then interpret a spreadsheet full of numbers with no narrative behind them. By the time the answer comes back, the moment for action has often passed. Multiply that across dozens of projects and portfolio managers, and the reporting team becomes a bottleneck rather than an enabler.

We think there's a better pattern — and we recently built and delivered exactly this for a client, using SAP Business Technology Platform's AI capabilities on top of an existing SAP ECC and BW landscape.

The use case: a project revenue assistant

Rather than build a general-purpose chatbot, we scoped the first agent tightly around a question business users ask constantly:

"How does actual project performance compare to plan, and why?"

The assistant lets a user ask, in natural language, for revenue, cost, and margin performance for a given project, month, quarter, or year — and returns not just the numbers, but the reason behind the variance: which cost elements moved, which milestones slipped, and how the current position compares to the baseline plan.

It turns a request that used to take a reporting analyst a day to fulfil into something a project manager can get an answer to in seconds, directly from a UI5 application.

How we built it on SAP BTP

The architecture keeps the AI layer strictly separated from the system of record, and reuses SAP's own security model end to end rather than inventing a parallel one.

Data layer

Plan and actual figures stay in SAP ECC and SAP BW. BW / HANA queries fetch the data, exposed to the cloud through SAP Cloud Connector and the BTP Connectivity and Destination services. The on-premise system remains the single source of truth.

AI layer

Reasoning sits in SAP AI Core within the Generative AI Hub, with SAP AI Launchpad for orchestration oversight. Prompts are written and versioned in AI Core's Prompt Registry; orchestration handles grounding, templating, and input/output filtering before anything reaches the foundation model.

Application layer

A UI5 application, fronted by SAP Build Work Zone and routed through the standard App Router and HTML5 App Repository, gives users a familiar, Fiori-consistent front end — not a bolt-on chat widget.

Identity & access

Non-negotiable: the agent gets no authorization model of its own. It runs on SAP Cloud Identity Services and respects the same role-based authorizations already governing ECC and BW. If a user can't see a project's margin in the source system, the agent won't surface it either.

Auditability

Every response — the question asked, the query executed, and the result set returned — is written back to SAP HANA, giving a persistent, queryable record for validating accuracy and satisfying internal audit and model-governance requirements.

Why the architecture matters as much as the model

It would have been faster to point a large language model at an exported CSV and call it done. We deliberately didn't, for three reasons that apply to any SAP-based AI agent project:

  1. Trust follows governance, not the model. Business and finance stakeholders relied on the assistant once they understood that authorization, data residency, and audit trail matched the standards of their existing reports. The LLM is the least trusted part of the chain by default — the surrounding architecture earns that trust back.
  2. The source of truth stays the source of truth. Querying BW directly rather than syncing data into a separate store avoids the classic "which number is right — SAP's or the AI tool's?" problem.
  3. Response logging turns a black box into an inspectable system. Storing the full result set alongside every answer means any variance explanation can be checked against the underlying data — making the assistant auditable, not just plausible.

Where this pattern goes next

Plan-vs-actual variance is a natural entry point because the data model is well understood and the value is immediately felt. But the same architecture — BW/ECC as source of truth, SAP AI Core for orchestration and reasoning, native SAP identity for access control, and HANA for response logging — extends cleanly to other finance and controlling questions:

  • Budget re-forecasting narratives
  • Intercompany reconciliation explanations
  • Asset and cost-centre anomaly detection
Don't start by asking which model to use. Start by asking how the agent will authenticate, where the data will actually live, and how every answer will be logged. Get those three right, and the model choice becomes the easy part.
